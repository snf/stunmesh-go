**Audit window:** 2026-09-13 01:01:47–11:01:47 UTC (ten hours; investigation ongoing).

**Audited tree:** `71a73228cd2bc001cdc5d485a16621a24bfae15a` (tree `638258efce44478f1c05b244d4fb24803ce16bc5`), release `v1.15.1` for the mobile core.

The audit branch and this root report are committed locally pending a disclosure decision; the public fork’s `main` remains at the audited upstream commit. This branch adds audit-only tests and this report; production code and NAS/VPS services were not changed.

## Deployment decision

**Do not deploy the current Android core as a security boundary.** A synthetic end-to-end test demonstrates that a discovery record produced with **either participant's** WireGuard *static* private key can inject multiline commands into the Android core's wireguard-go configuration, remove that peer's preshared key, enroll a new peer, transfer its allowed-IP route, and deliver the route's plaintext traffic to the new peer after a normal WireGuard handshake. The actor does **not** need the PSK or a handshake to change configuration. With valid generated peer keys, the actor must hold either the configured peer's or the local device's static private key; an arbitrary DHT writer holding neither failed the control test. A malformed low-order configured key removes even that discovery barrier (G-14). A separate malicious-profile import can inject an unlisted peer through the initial endpoint field while leaving the app's route valid. These are **high-severity blockers** if the configured peer list and PSK are meant to preserve access control.

The strict requirement that **all peer authentication be handled by WireGuard modules** is **not met**. `internal/crypto/endpoint.go` authenticates discovery JSON with `golang.org/x/crypto/nacl/box` using the same static X25519 keys, outside a WireGuard handshake and without its PSK. This is a documented design choice, not an apparent hidden backdoor. If the requirement is relaxed to “discovery is merely an untrusted address hint and only WireGuard authorizes peers and packets,” G-01 must still be fixed so discovery cannot alter trusted peer keys, PSKs, or routes.

No deliberate backdoor or evidence of a compromised downloaded dependency was identified in the inspected source and release. This is a bounded result, **not proof of absence**. Unsigned tags and non-bit-identical Go AAR rebuilding leave provenance risk.

## Architecture, authentication, and external dependencies

The Go daemon uses STUN to learn its public UDP mapping, encrypts an endpoint record, and writes/reads it through a storage plugin. The built-in OpenDHT plugin uses a configured proxy, normally HTTPS, only for record exchange. **It is not an ongoing WireGuard packet relay.** When Linux `proxy.enabled` is selected, `internal/wgproxy` is a local UDP relay between its outward socket and the WireGuard interface, not a remote hop. Tunnel traffic is direct peer-to-peer after successful punching. There is no TURN/DERP relay fallback, so some NAT pairs will not connect. STUN and DHT access remain needed for refresh/recovery. The STUN server observes the probe's public IP/port; the DHT proxy observes requests, source IP, public record index and timing. Neither receives WireGuard plaintext packets through this architecture, but both can impair discovery availability. The proxy's Linux full-tunnel escape path logs `SO_MARK`/route-probe failures and continues without marking its outer socket (`internal/wgproxy/escape_linux.go`); with a covering default WireGuard route that can prevent discovery/egress. The planned NAS trial uses split tunnel routes, so this is a conditional availability concern, but any later full-tunnel mode needs a rootless-namespace test that verifies the actual outer UDP route.

| Boundary | Check | Inside a WireGuard module? | Consequence |
| --- | --- | --- | --- |
| OpenDHT index/values | Public read/write; index derived from ordered public keys | No | Public writer can affect availability; a properly generated-key record cannot be decrypted or forged without a private key. G-14 is the malformed-key exception. |
| Discovery record | NaCl `box.Open` with static X25519 pair | **No** | A static-key holder can author it without the WG PSK/handshake. |
| STUN response | Mobile checks transaction ID; Linux raw path does not | No | Gives an address hint, not peer authorization. |
| WG handshake/data | `wireguard-go` on Android; kernel/official WG via `wgctrl` on desktop | **Yes** | Ordinary packets retain WG authentication unless G-01 changes the authorized peer set. |
| Optional Cloudflare store | Cloudflare bearer API token | No | Authenticates storage calls, not WG peers. Not needed for OpenDHT. |

The [WireGuard PSK is mixed into its handshake](https://www.wireguard.com/protocol/), not NaCl records. OpenDHT is [public read/write storage](https://github.com/savoirfairelinux/opendht) with [GET/POST on the hash index](https://github.com/savoirfairelinux/opendht/blob/be210e27da674be618e2d4cbc422a897b3daff96/src/dht_proxy_server.cpp). Threats below distinguish an arbitrary DHT writer, a compromised peer static key, a malicious configured peer, an on-path STUN actor, imported local configuration, and a compromised build account.

## Findings

### G-01 — High: discovery and imported text change Android WireGuard authorization

**Demonstrated.** `mobile/controller.go:288–335` decrypts JSON and forwards a selected endpoint string without syntax validation. `mobile/uapi.go:57–62` interpolates it into newline-delimited wireguard-go UAPI. An injected newline and `public_key=` starts a second peer definition; `preshared_key=` and `allowed_ip=` change security state. `update_only=true` applies only to the first peer. `mobile/audit_security_test.go` (`TestAuditDiscoveryRecordCanEnrollPeer`) uses generated keys, in-memory TUNs and a fake store in an isolated namespace. It proved rogue enrollment, PSK removal, route takeover and actual plaintext packet delivery after a real WG handshake. Both peer-static-key and local-static-key forged records succeeded in the race-enabled end-to-end test; an unrelated-key control changed nothing for valid generated keys (`security-audit-evidence/mobile-either-static-key-forgery.txt`). A second race-enabled test showed that if a later injected UAPI line is invalid, `IpcSet` returns an error **but leaves the already-created rogue peer and route installed**; checking only the update's error is insufficient (`security-audit-evidence/mobile-rejected-uapi-persists-peer.txt`). G-14 demonstrates the exceptional low-order-key case. This tests the same Go core bundled into Android, but not an actual Android OS VPN. The desktop daemon instead parses a host/port and passes a typed endpoint through `wgctrl` or an argument vector to `wg set`; this audit did not demonstrate the multiline UAPI injection on that desktop path.

**A separate import path is also demonstrated.** `mobile/uapi.go:37–52` interpolates imported `endpoint` and `allowed_ips` strings into the initial UAPI before discovery. `TestAuditImportedEndpointTransfersValidRouteToHiddenPeer` passed an app-shaped JSON profile with one listed peer, a valid AllowedIPs CIDR and an endpoint containing a newline through `parseConfig` and `buildUAPI`. The hidden peer took that valid route without the listed peer's PSK (`security-audit-evidence/mobile-imported-endpoint-hidden-route.txt`). A second test showed that a newline inside AllowedIPs alone can install an unlisted peer and route in wireguard-go (`security-audit-evidence/mobile-imported-allowed-ip-hidden-peer.txt`); Android's TUN builder may reject that malformed CIDR, so actual phone traffic effect of this latter variant remains untested. Both require a user to import/select a malicious profile or another local configuration compromise; a DHT writer cannot set these fields directly. The Android report tests that its YAML importer preserves both kinds of hidden lines through the JSON bridge.

**Fix:** Parse as `netip.AddrPort`, require the expected IP family, reject controls and invalid/non-unicast endpoints, and render only the canonical parsed value. Make UAPI rendering use typed values; parse imported initial endpoints and AllowedIPs as typed addresses/CIDRs and reject controls at both the app and core boundaries. Assert after every update that peer keys, PSKs and AllowedIPs still equal the trusted configuration. Preserve these adversarial integration tests in CI.

The raw-string UAPI renderer entered with the original mobile bind feature commit `9df52b00713319b5c2b3ee2b36c8f5d2386abea1` in July 2026; its commit message described run-time endpoint updates over UAPI. The history makes this look like a missed input boundary in an early implementation, but it cannot establish intent.

### G-02 — High policy mismatch: discovery uses a second authenticator

**Confirmed from source and synthetic tests.** `internal/crypto/endpoint.go:28–66` uses [NaCl box](https://pkg.go.dev/golang.org/x/crypto/nacl/box), which explicitly authenticates and encrypts messages, on WG static key material. `internal/entity/peer_id.go:29–46` derives public SHA-1 DHT indices from public keys. There is no WG handshake, PSK verification or WG module call before accepting a decrypted record. Shared-secret box ciphertext can be generated by either participant; `internal/crypto/audit_security_test.go` confirms a record can be reflected into the reverse slot because sender/slot context is not authenticated. **An arbitrary DHT reader/writer who knows the two public keys can copy an existing ciphertext into the opposite public slot and have it decrypt there**, making a peer mistake its own published endpoint for the other's. With correctly generated keys, that is an availability attack, not arbitrary plaintext forgery or a WG packet-authentication break. G-14 is the exceptional malformed-key case in which an outsider can decrypt and forge a new record. This design also brings the desktop WireGuard **private key into the STUNMESH daemon's address space**: `internal/wg/client_ctrl.go:35–49` reads it through `wgctrl`, and the alternate CLI backend parses it from `wg show ... dump` (`internal/wg/client_cli.go:50–109`). A compromise of the daemon therefore exposes the static key directly. An executable plugin also shares the daemon's file and interface access unless separately confined, although access to the parent process's memory depends on OS permissions. The PSK is not part of the NaCl record authenticator; G-01 shows why possession of **either** static key without a PSK is still dangerous to the Android controller.

**Choice:** A literal WireGuard-only authentication design treats rendezvous values as untrusted endpoint hints, permits them to change **only** a preconfigured peer's typed IP:port, and leaves peer identity, PSK and routes under local/WG control; this gives up authenticated DHT record origin and may expose endpoint metadata if the hint is plaintext. In that design the desktop helper should stop reading the WireGuard private key altogether, and the Android controller should stop reusing the app's WireGuard private key for discovery; the embedded WireGuard module still needs its own private key. Keeping NaCl only as a privacy codec while never granting it authorization would be a **policy reinterpretation** to agree explicitly. A separate discovery key or authenticated sender/slot/version context reduces key reuse/reflection but remains authentication outside WG, so does **not** satisfy the literal original policy. No variant can force an uncooperative public DHT to return fresh values, so availability remains a separate choice.

The explicit NaCl `box` endpoint encryption appears in an August 2024 serializer refactor (`b51e89cba158554f46c44955f23f3787be29780c`), well before the mobile port. This supports that the second authenticator is a long-standing, documented design choice; it does not make it compatible with the requested policy.

### G-03 — Medium: public DHT writer can eclipse a valid record

**Demonstrated with a synthetic proxy response.** `internal/plugin/builtin/opendht/opendht.go:246–285` selects the largest plaintext envelope `Ts` **before** cryptographic decryption. The [upstream OpenDHT proxy POST handler](https://github.com/savoirfairelinux/opendht/blob/be210e27da674be618e2d4cbc422a897b3daff96/src/dht_proxy_server.cpp) passes a syntactically valid value to `dht_->put` without checking a STUNMESH peer identity; an actual public proxy may also impose operational limits. A writer knowing public peer keys can post a far-future timestamp and invalid ciphertext. `Get` returns the poison and valid peer decryption fails, impairing reconnection until the poison expires/disappears. A second test copied an old **valid** ciphertext into a new far-future envelope; `Get` returned it and decryption yielded the stale endpoint instead of a newer valid record. This means decrypting candidates alone would not stop replay. Even two honest publications within one Unix second have equal `Ts`: a synthetic proxy set containing both in either order made `Get` choose the first line, so a stale endpoint can win an ordinary rapid refresh (`security-audit-evidence/opendht-equal-second-records.txt`). `Magic` is plaintext in every public envelope, so changing it does not authenticate a writer. Existing live tunnel packets are not decrypted or forged. Both cases are in `internal/plugin/builtin/opendht/audit_security_test.go`; no live public DHT record was changed during the audit.

**Fix, if the separate NaCl record authenticator is deliberately retained:** Bound response/candidate size; fetch candidates and decrypt with expected peer before selection; put a high-resolution timestamp or monotonic sequence, sender and slot **inside** the authenticated record and reject old/future or wrong-context values. Maintain a last-seen floor where feasible, with an explicit restart/recovery policy. Select only among valid records, and permit fallback after a malformed successful proxy response. **Under the literal WireGuard-only option in G-02**, DHT values are untrusted hints and cannot carry an authenticated freshness claim. Bound candidates and retry alternate values/proxies, but accept that a public writer or proxy can prevent discovery; WireGuard still rejects unauthenticated tunnel peers. Neither design can force a public DHT operator to return fresh values.

### G-04 — Medium: raw STUN path accepts unsolicited address replies

**Demonstrated with synthetic loopback traffic in an isolated network namespace.** `internal/stun/helper_socket.go:29–67` creates a random transaction ID but never compares it after `Read`. `internal/stun/stun_linux.go:204–226` parses any BPF-matched reply without verifying sender or response type against the request. `internal/stun/audit_security_test.go` sent a forged Binding Success from a different loopback address; the attacker-chosen reflexive endpoint was accepted. This manipulates endpoint advertisement/availability, **not** WG packet authentication. It needs the ability to send to the probe port at the right time or influence the underlay. The same unvalidated `Connect` helper is compiled for Darwin/BSD pcap discovery, although this audit network-tested only Linux. The local proxy path `internal/wgproxy/demux.go:95–107` checks both ID and sender; the Android shared socket checks ID but not sender.

**Fix:** Require matching request ID, expected server IP:port, response class/type and valid length on every path; discard mismatches until timeout. This follows [RFC 8489 response checks](https://www.rfc-editor.org/rfc/rfc8489.html). Rootless Podman proxy mode avoids raw-socket privilege but does not excuse the raw-path defect.

### G-05 — Medium: DHT HTTP response is unbounded

**Confirmed from source; memory-exhaustion exploit not run.** `opendht.go:192–223` uses `io.ReadAll(resp.Body)` before status checking, and `Get` processes every line. A malicious or broken configured proxy can force unbounded allocation; a successful malformed body also prevents request fallback. `internal/plugin/builtin/config.go:84–95` accepts a configured OpenDHT `timeout` of zero or less; Go's `http.Client` then has no request deadline, so a stalled proxy can block the refresh cycle until its outer context is cancelled. A targeted race-enabled test confirmed four accepted zero/negative forms (`security-audit-evidence/opendht-nonpositive-timeout.txt`). This is a local-configuration precondition, not something a DHT writer can change. The optional built-in Cloudflare plugin has the same unbounded read. TLS verifies a proxy identity, not response safety.

**Fix:** Use a strict `io.LimitReader` cap, stream a limited number of limited-size entries, reject implausible timeout values, and retry alternate configured proxies on invalid successful responses.

### G-06 — Optional process plugins enlarge the trust boundary

`internal/plugin/manager.go:84–94` accepts `exec`/`shell`; `internal/plugin/exec.go:83–97` and `internal/plugin/shell.go:81–100` run a configured executable. This is documented and requires a local config/import choice; an arbitrary DHT writer does not set the executable. Yet the Android core has no allowlist despite Android comments promising built-ins only. `TestAuditMobileCoreAcceptsExecutablePlugin` demonstrates execution in a Linux build of the mobile core; Android OS execution is unverified. The optional `contrib/cloudflare-shell/cloudflare-shell.sh:45` also runs `source /dev/stdin` on unescaped shell-protocol assignments. An isolated synthetic fixture with `STUNMESH_KEY=$(printf reached >...)` created its marker before any Cloudflare call, confirming shell evaluation. Normal daemon calls use hash/ciphertext hex, limiting this flow, but the generic helper is unsafe with untrusted values. The optional Cloudflare exec helper takes `-token` as a command-line argument (`contrib/cloudflare/main.go:128`), exposing that credential to process-argument inspection wherever the host/container permits it. The optional `contrib/opendht`, `opendht-shell`, and `cloudflare-shell` smoke tests passed against local fake services; those tests do not remove the trust-boundary concerns.

**Fix for the home build:** ship only the built-in OpenDHT plugin; reject `exec` and `shell` at Android import/core boundaries and home configuration validation. Omit the optional shell helper.

### G-07 — Supply-chain and binary provenance gaps

Core `go.mod` declares 14 direct and 16 indirect requirements. `go list -m all` resolved 58 external modules (59 including the main module), while the published Linux amd64 daemon's Go build information lists 19 linked dependency modules and the Android all-builtins AAR linked 16 Go modules including the local module. The Linux binary does not link the wireguard-go packet engine because the desktop daemon configures an existing WireGuard interface; the Android AAR does link it. All downloaded module and go.mod hashes matched `sum.golang.org`, and `go mod verify` passed. An independent comparison of **all 14 declared direct Go modules** to official source checkouts at their pinned commits/tags found **3,230/3,230 delivered files byte-identical**, including the WireGuard packet engine/control API, Pion STUN, YAML, NaCl-bearing `x/crypto`, the fallback CA bundle, and the niche `go-pcap` module (`security-audit-evidence/critical-go-source-module-comparison.json`). Of these, one is a copied repository-root LICENSE; 164 Git files omitted from the corresponding main module archives are entirely nested-module subtrees, and there were no unexpected delivered files. This strengthens source provenance for the direct dependency graph, but does not audit every dependency line, prove publisher intent, certify the CA set, or cover all 16 indirect modules. The optional separate `contrib/cloudflare` graph had 53 resolved modules and passed checksum/race checks but is unnecessary for OpenDHT. Public checksum consistency does not certify maintainer intent. The [direct dependency triage](security-audit-evidence/direct-dependency-triage.md) maps each declared module to its role and the checked binary families. The critical direct libraries come from [WireGuard](https://git.zx2c4.com/wireguard-go/about/), [Pion](https://github.com/pion/stun), Go `x/*`, and the [YAML organization's maintained fork](https://github.com/yaml/go-yaml); their full source and the Go/Android/OS platform internals were not independently audited. The more niche `github.com/packetcap/go-pcap` is declared directly but absent from the checked Linux and Android binaries; it is used on Darwin/BSD paths. The pinned official `wireguard-go` commit is one commit behind its 2026-09-13 HEAD: the intervening Linux TUN fix clears a virtio header after a GRO-table deletion ([official commit](https://git.zx2c4.com/wireguard-go/commit/?id=ecfc5a8d54462e18e13c72173e2623d16d8e25a0)). Android cross-builds include that Linux source, but the affected path requires `IFF_VNET_HDR` on the VPN TUN fd; without a device this audit did not establish reachability or an exploit (`security-audit-evidence/wireguard-go-upstream-delta.txt`). Update and retest the pinned core before a fork release.

The [official WireGuard Go implementation](https://git.zx2c4.com/wireguard-go/about/) and `wgctrl` supply the packet engine/desktop control API; `golang.org/x/crypto` supplies NaCl box and X25519; [Pion STUN](https://github.com/pion/stun) supplies desktop STUN parsing; `zerolog`, `mapstructure` and YAML support logging/configuration. The Android core's custom STUN parser means Pion is absent from its 16-module linked list. `github.com/packetcap/go-pcap` is used for Darwin/BSD tests/source, not the Android binary; `go.uber.org/mock` is test-only; `golang.org/x/mobile` is a build/binding requirement. `github.com/google/wire` and `wgctrl` still appear in the Android link graph via shared packages, so a mobile-specific core split could reduce the shipped dependency closure further. These classifications come from source imports and `go version -m`/build-tag variants; they are **not** a line-by-line audit of upstream dependency source. The OpenDHT-only build removed the optional Cloudflare implementation from the native image, but executable plugin paths still require a source change to disappear.

An independent `GOOS=android GOARCH=arm64 CGO_ENABLED=1` import-closure check with the release's `mobile,builtin_all` tags found 265 packages and 15 external modules (`security-audit-evidence/mobile-android-dependency-paths.json`). It traced `wgctrl` and three `mdlayher` netlink modules through mobile → `internal/ctrl` → desktop `internal/wg`, YAML through `internal/ctrl` → desktop `internal/config`, `google/wire` through `internal/crypto`, and `mapstructure` through the common plugin manager. The phone's actual data plane uses embedded `wireguard-go`, so the desktop control/configuration dependencies are avoidable build-graph entries. This is package-import evidence, **not** proof that every dependency contributes retained machine code. Move shared endpoint types/interfaces into a small package, isolate desktop controller/DI wiring, and exclude `exec`/`shell` plugin constructors from mobile builds; then compare the resulting AAR module and executable-code closure before claiming a smaller trust surface.

`govulncheck` found three module-level advisories in `golang.org/x/crypto v0.55.0` (OpenPGP and SSH), but no affected OpenPGP/SSH package or symbol in the production import closure (`security-audit-evidence/govulncheck-core-summary.json`). The optional Cloudflare module had zero reported reachable findings. An independent OSV batch query of all 58 resolved core modules reported advisories in four modules: `x/crypto` plus `goldmark` (XSS), `x/image` (VP8L memory use), and `x/mod` (checksum transparency verification); the latter three are **not linked** into the checked Linux daemon or Android AAR. The separately resolved Cloudflare module graph reported `x/crypto` and `x/mod`. The audit build used Go 1.27.1, past the fixed toolchain version for the `x/mod` advisories. These are module-presence results, not reachable exploit findings (`security-audit-evidence/go-osv-querybatch.json`, `security-audit-evidence/contrib-cloudflare-osv-querybatch.json`). Upgrade after compatibility checks. `gosec` scanned 96 files/9,668 lines in the core and reported 21 issues, mostly integer conversions, SHA-1, math/rand ICMP IDs, configured process plugins and test code (`security-audit-evidence/gosec-core-summary.json`). A separate default-rule scan of the nested Cloudflare module's two source files/217 lines emitted zero issues (`security-audit-evidence/gosec-contrib-cloudflare-summary.json`). SHA-1 here indexes high-entropy public keys; it is **not** a MAC/signature. Gosec missed G-01.

The official `v1.15.1` AAR SHA-256 is `c0de0320a9f13f70f3d0069abccb80035383a1fcb1f591d2362db58b2960e520`. An initial source rebuild with matching Go 1.27.1, modules, tags and linker flags produced `9c2df68879664a4815841a3e901109d1376cbd5f7d1e8a0da0dbbd3542a94310`: **not bit-identical**. All nine AAR entry names, generated Java class names, and each ABI's Go function-name multiset match (7,889–7,979 per ABI). Among 21 generated Java JAR entries, only `go/Seq$GoRefQueue$1.class` differs, by a constructor `MethodParameters` attribute; its instruction and line listing is identical (`security-audit-evidence/go-aar-java-class-comparison.json`). ARM64's 7,889 decoded Go functions have identical order and individual sizes; 2,897 have identical raw code hashes. The 3,210,336-byte `.text` sections differ in 65,916 bytes / 40,357 instruction words. Every changed word retains its opcode and registers; only ADRP/ADR displacement, ADD immediate, or load/store offset fields differ.

An audit-only rebuild then bind-mounted the same source, Go module cache and Go 1.27.1 toolchain at the paths embedded in upstream CI output. A single local change to the `gomobile` **build tool**, not STUNMESH source, fixed its temporary directory to the upstream path recovered from the AAR. That AAR's SHA-256 is `429094be6ab70cce2e492d8e85e2de3736cec165259ff8b6374a21ffd4583880`. Its ARM64 and x86_64 ELF libraries have the same length as upstream and differ **only** in the Go and GNU build-ID notes (78 and 79 bytes respectively); all executable code, read-only data, relocation tables, build metadata and other sections are byte-identical. A 32-bit comparison found x86 `.text`, `.rodata` and Go function metadata byte-identical. ARMv7 `.rodata`, function names/order/offsets/sizes and Go function metadata are identical. Every changed ARMv7 `.text` 32-bit word differs by exactly `+8` (32,594 words) or `+2` (152 words), matching the extra GNU build-ID note shifting `.text` by 40 bytes and aligned `.plt`/`.data.rel.ro` by 48 bytes; branch immediates encode the eight-byte target difference in words (`security-audit-evidence/go-aar-armv7-layout-normalization.json`). This is strong layout correspondence, but **not** a formal proof that every changed instruction has identical semantics. The AAR archive, generated Java JAR and complete 32-bit ELF libraries are not bit-identical. This is very strong evidence against an additional release-only backdoor in the matched 64-bit native code, with useful but weaker evidence for 32-bit code; it does not prove the source is safe or the whole AAR reproducible. The annotated upstream `v1.15.1` source tag is unsigned (`security-audit-evidence/go-release-tag-signature.txt`). GitHub release digests confirm integrity relative to GitHub metadata, not independent publisher identity. Summary comparisons are in `security-audit-evidence/go-aar-deterministic-path-comparison.json` and `security-audit-evidence/go-aar-32bit-comparison.json`.

Upstream release workflows use `gomobile@latest`, `GO_VERSION: stable`, `golang:latest` and version-tagged Actions; the Docker image builds/copies optional plugins. Its `COPY . .` also has no `.dockerignore`, so a build context containing local credentials would enter the builder layer/cache even though only binaries reach the final scratch image. The final image declares no `USER`, so it runs as UID 0 inside a rootless Podman namespace and can access whatever mounts that mapped user is granted; deployment must check host UID/GID mappings and mount permissions. The OpenWrt installer fetches mutable latest binaries without hash/signature verification and is inappropriate here. The privileged CLA workflow loads `tjjh89017/stunmesh-cla@main`; the [inspected action at HEAD `6b6636b`](https://github.com/tjjh89017/stunmesh-cla/blob/6b6636bb073860f857f59a3efee6d08d17fe8c33/action.yml) delegates to `contributor-assistant/github-action@v2.6.1` with `GITHUB_TOKEN` and the optional CLA-signature PAT. No custom executable code was found in that wrapper, but it is another mutable privileged dependency; the personal fork does not need it. An OpenDHT-only AAR build with `builtin_opendht mobile` succeeded and removed the Cloudflare implementation/URL from the ARM64 image, but `exec` and `shell` remained linked through the shared manager. For the fork, pin Go/gomobile/NDK/base image/actions, restrict the build context, remove the unused executable plugin paths in source, use a minimal built-in-only Podman image, record SBOM/provenance and hashes, and build the AAR/APK/container from reviewed local source.

The release matrix gives its build jobs `contents: write`, and checkout leaves `persist-credentials` at [the documented default `true`](https://github.com/actions/checkout/blob/main/README.md). In v7, the credential is kept in a runner-temporary file rather than directly in `.git/config`, but subsequent job steps can still run authenticated Git commands. A compromised downloaded build tool or action in a release job could replace/upload artifacts or access that credential; this is a workflow trust consequence, not evidence of an existing malicious dependency. Split build/test from publishing, use read-only permissions during compilation, disable persisted checkout credentials where unnecessary, verify exact artifact hashes at the publication boundary, and give write permission only to the final upload job.

An additional [zizmor](https://docs.zizmor.sh/usage/) v1.30.1 offline auditor scan of the Go workflow/composite-action definitions produced 182 raw warnings, including 35 high-severity template-injection and 51 high-severity unpinned-action warnings (`security-audit-evidence/zizmor-ci-triage.json`). Its tag-input flags corroborate the independently reproduced G-12 path, but many other action inputs have static or lower-trust callers and were **not** individually shown exploitable. The scan performed no online audits and, by the tool's own documented scope, does not inspect external shell scripts. Treat counts as triage leads, not 182 confirmed vulnerabilities.

**All 16 published `v1.15.1` server executable payloads were reproduced byte-for-byte** from the exact tagged commit `bc0922007e81e1a9abdff38988d2cb8c44a4d208` using Go 1.27.1, `CGO_ENABLED=0`, `-trimpath`, `-ldflags '-s -w'`, and the release's `builtin_all` (plus `embedca` for CA variants) tags. This covers every released Linux, macOS and FreeBSD binary and the executables extracted from both Windows ZIPs. The Linux amd64 regular and CA binaries, for example, match SHA-256 `d57409d6fc4a34e5ba66160d51dc85635bb8b261038ae59c49f424e8bd68777b` and `c5884bf27756ad906981585e7d92ebd743fcaaa43e407a5d3275d05472c19093`. Every downloaded asset's SHA-256 also matched GitHub release metadata. Exact platform/architecture hashes, source/build inputs and payload comparisons are in `security-audit-evidence/server-all-platform-release-rebuild.json`; the first two Linux results are also in `security-audit-evidence/server-release-rebuild.json`. The Windows ZIP *containers* themselves were not reconstructed. The separately published 9,080-byte gomobile Java **source JAR** also reproduced byte-for-byte (`security-audit-evidence/mobile-sources-jar-rebuild.json`). These matches provide strong evidence that the released server executables correspond to the reviewed release source and dependency/toolchain inputs; they do not prove the source is safe, authenticate first publication by GitHub, or cover optional plugin archives or the separate AAR/APK.

The inherited `.github/workflows/cla.yml` uses `tjjh89017/stunmesh-cla@main` on `issue_comment` and `pull_request_target` with `actions: write`, `pull-requests: write` and `statuses: write`, and passes an optional PAT secret. A mutable upstream branch therefore controls code in a privileged workflow; this is a **future compromise path if Actions are enabled on the fork**, even though no malicious change or secret theft was observed. [GitHub recommends pinning third-party actions to a full commit](https://docs.github.com/en/actions/reference/security/secure-use#using-third-party-actions). On 2026-09-13, GitHub Actions were disabled on the new `Owner` Go and Android forks; the API readback confirmed `enabled: false`. Before re-enabling, remove the unnecessary CLA workflow, pin/review each external action, and give release jobs only the permissions and secrets they require.

### G-08 — Medium availability: default publish interval meets OpenDHT's expiry boundary

`internal/config/config.go:27` defaults refresh to ten minutes, and `mobile/config.go:112–114` defaults to 600 seconds. OpenDHT's [default value expiration is ten minutes](https://github.com/savoirfairelinux/opendht/blob/be210e27da674be618e2d4cbc422a897b3daff96/include/opendht/value.h), also noted in STUNMESH's OpenDHT plugin comments. A routine network delay or one failed cycle can therefore leave no valid endpoint record before the next successful publish. This is an availability fault, not unauthorized access. `dedup=true` on an OpenDHT plugin is worse: it can skip unchanged re-publication indefinitely. Set a refresh interval comfortably below expiry (for example, one minute), keep OpenDHT dedup off, and test multi-hour operation plus reconnect after a failed refresh.

### G-09 — Low availability: non-positive desktop ticker intervals can crash the daemon

`internal/config/config.go:273–330` validates several fields but not `RefreshInterval` or the global ping-monitor interval/timeout. `internal/daemon/daemon.go:109` calls `time.NewTicker` with the refresh value, which panics for non-positive intervals. `TestAuditZeroRefreshIntervalPanicsAfterConfigAcceptance` proves `config.Load` accepts `refresh_interval: 0s` and `Daemon.Run` then panics. `TestAuditNonpositivePingCadencePassesConfigLoad` additionally proves it accepts `ping_monitor.interval: -1s` and `timeout: 0s`; when at least one peer enables ping, `internal/ctrl/ping_monitor.go:295,347` creates tickers from those values and would panic in its worker goroutines (`security-audit-evidence/go-audit-nonpositive-ping-cadence.txt`). The latter worker path is source-confirmed, not exercised as a full daemon run. These require a local configuration mistake or write access; they are not remote exploits. Reject all three intervals below a safe positive minimum during configuration load and keep regression tests.

### G-10 — Low availability: desktop proxy mode wraps out-of-range discovered ports

`internal/ctrl/establish.go:112–118` parses a decrypted endpoint port as an unrestricted `int`, and `internal/wg/proxy_client.go:101` narrows it to `uint16`. `TestAuditProxyWrapsOutOfRangeDiscoveredPort` proves port `65537` is accepted and programmed as port `1` in proxy mode. A valid discovery-record author can already choose a valid port directly, so this is input-validation/availability weakness, **not a new authentication bypass**. Require a numeric port in `1..65535` before either desktop backend uses it.

### G-11 — Medium conditional risk: DHT proxy redirects can cross the network boundary

`internal/plugin/builtin/opendht/opendht.go:140–160,192–223` uses Go's default `http.Client` redirect policy. In `TestAuditConfiguredProxyCanRedirectIntoLocalNetwork`, a configured synthetic **HTTPS** proxy returned an HTTP 302 and the client followed it to an unrelated **HTTP** loopback URL inside an isolated namespace. A compromised configured proxy, or an on-path actor when the proxy is configured with `http://`, can therefore induce requests from the daemon/phone's network context to other addresses, including reachable LAN services. The exact impact depends on routing and the target service; the test did **not** demonstrate a router exploit, secret extraction or WireGuard peer authentication bypass. Disable redirects for DHT requests, or allow only same-origin HTTPS redirects with an explicit limit; use HTTPS proxy URLs.

### G-12 — High release-artifact risk: tag name executes in composite action shells

**Demonstrated locally without a GitHub run.** The release workflow takes a tag name from `git describe --tags --dirty`, passes it as `inputs.tag`/`inputs.version`, and `.github/actions/build/action.yml:43–44`, `build-aar/action.yml:49–50` and `archive-plugins/action.yml:35–37` interpolate those inputs directly into `run:` shell scripts. In a temporary local Git repository, the valid tag `v$(printf${IFS}AUDIT_CANARY)` emerged unchanged from `git describe`; substituting it into the actual AAR action line executed Bash command substitution (`security-audit-evidence/go-release-tag-injection.json`). [GitHub warns that context expressions are expanded into generated shell scripts and ref names can contain untrusted input](https://docs.github.com/en/actions/concepts/security/script-injections). No tag was pushed to GitHub, so this does not establish remote acceptance of that particular name or actual credential theft. The precondition is control over a tag that triggers the release workflow; tag protection may restrict it. A tag-triggered release job has write-capable release credentials and produces the daemon, plugin and Android AAR artifacts, so command execution there compromises artifact trust independently of the source code reviewed here. The two `Owner` fork Actions are disabled.

**Fix:** Pass the tag into each step through `env:` and use quoted shell-variable expansion, not direct expression substitution in a script. Validate a narrow release-tag pattern, protect release tags, pin/review external actions and the privileged CLA workflow before enabling releases. Review all composite action inputs that reach shell scripts.

### G-13 — Medium local availability: a malformed YAML mapping panics during config load

**Found by coverage-guided fuzzing and reproduced.** `internal/config/config.go:203–221` passes a YAML-decoded map with nested arbitrary mapping keys to `github.com/go-viper/mapstructure/v2@v2.5.0`. A 54-byte minimized synthetic suffix using an anchor on an empty mapping key decodes without a YAML error to `map[interface{}]interface{}{nil: 0}` and causes `mapstructure`'s `decodeStructFromMap` at `mapstructure.go:1732` to dereference the nil key and panic, rather than returning a configuration error (`security-audit-evidence/config-yaml-anchor-panic.txt`, `internal/config/audit_security_test.go`). The daemon reads this document from a **local configuration file at startup**; no remote DHT writer was shown to invoke the loader. A local actor who can replace the config can already disrupt startup, so this is primarily robustness and recovery, not a remote entry bypass. The mobile core receives JSON instead of this YAML/mapstructure path.

**Fix:** Reject non-string/null mapping keys and aliases before mapstructure decoding, and make malformed input return a bounded error. Keep the minimized regression in normal tests after fixing it. Assess upstream mapstructure separately; a dependency patch alone may not supply all input validation the application needs.

### G-14 — Medium, conditional: low-order peer key makes discovery records publicly forgeable

**Demonstrated with a malformed all-zero peer key.** The mobile JSON parser and wireguard-go UAPI accept a 32-byte all-zero `public_key` as a configured peer (`mobile/audit_security_test.go`, `TestAuditMobileAcceptsLowOrderPeerKey`). The desktop `DeviceConfig.GetConfigPeers` also checks only base64 decoding and byte length, not curve point validity (`internal/config/device.go:176–205`); the Android consequence below was tested, while a desktop low-order-key attack was not. The imported `golang.org/x/crypto/nacl/box` calls deprecated `curve25519.ScalarMult`, which [returns an all-zero shared point for a low-order public key](https://pkg.go.dev/golang.org/x/crypto/curve25519); every private scalar then derives the same publicly computable box key. `TestAuditLowOrderPeerKeyMakesDiscoveryRecordPublic` decrypts a record made by one private key with an unrelated one. A synthetic controller test (`TestAuditLowOrderPeerAllowsOutsiderToEnrollRoguePeer`) shows that an arbitrary writer who knows the local public key and can write the peer's DHT slot can forge a record and, via G-01, enroll an unconfigured WireGuard peer **without either configured private key or PSK** (`security-audit-evidence/go-low-order-key-composition.txt`). This is a **misconfiguration-dependent amplification** of G-01, not an attack against correctly generated peer keys. WireGuard's own handshake rejects the all-zero static shared secret, so the malformed peer itself cannot connect; the injected new peer is different and can be valid. No public DHT or Android phone was used.

**Fix:** Reject all-zero/low-order peer public keys before storing or publishing anything, using an X25519 operation that returns an error on low-order points; validate imported configuration before tunnel start. G-01's typed, non-authorizing endpoint handling is still required because a legitimate or compromised valid peer can otherwise inject UAPI commands. Treat the DHT record as untrusted regardless of its apparent box authentication.

### G-15 — Low, conditional: desktop UDP proxy loses a peer after endpoint collision

**Demonstrated in an audit-only unit test.** The optional desktop `internal/wgproxy/demux.go:150–169` maintains a forward map from public UDP source to peer and a reverse map from peer to source. If two configured peers are temporarily programmed to the **same** source address, the second overwrites the forward entry. When the first peer is later moved to a different address, `Program` blindly deletes the shared old forward entry and the second peer's packets are dropped even though its reverse entry still points there (`security-audit-evidence/wgproxy-endpoint-collision.txt`). This requires a duplicate endpoint from configuration/discovery or a transient mapping collision; ordinary distinct endpoints are unaffected. It is an availability failure in proxy mode, **not** a WireGuard authentication bypass. The Android shared-socket bind does not use this desktop demultiplexer.

**Fix:** Make endpoint ownership explicit and update both maps consistently on collisions/reprogramming, or reject ambiguous endpoint assignments. Keep a regression test for two peers sharing a source and then one moving away.

### G-16 — Medium availability: Linux raw STUN fallback cannot recover after a bad first reply

**Demonstrated with two synthetic loopback STUN servers in an isolated network namespace.** `internal/stun/stun_linux.go:157–193` starts one raw-socket reader and returns from that goroutine after delivering its **first** packet. `internal/stun/helper_socket.go:29–67` then parses the packet; if it is a valid STUN response without the required XOR-MAPPED-ADDRESS, `Connect` returns `ErrNoMappedAddress`. The resolver proceeds to its next configured STUN server, but nobody is reading the raw socket. `TestAuditRawSTUNFallbackCannotReadSecondReply` proved that the second server received the request and sent a valid response, yet the client timed out (`security-audit-evidence/stun-raw-fallback-consumed-listener.txt`). It requires the first server or an on-path actor to send one unusable response, or an ordinary transient malformed reply. It does **not** affect WireGuard packet authentication. The Android shared-socket and desktop proxy-backed STUN paths use different listeners.

**Fix:** Keep the reader active for the full discovery operation, and validate source, transaction ID, response type and mapped endpoint before consuming a reply. Continue reading after a malformed/mismatched packet until the attempt times out. Add a real two-server fallback regression for the raw path, not only a resolver test with a mock client.

### G-17 — Medium conditional credential disclosure: OpenDHT URL userinfo reaches logs

**Demonstrated with synthetic credentials and a local failing proxy.** OpenDHT accepts `http(s)://user:password@host` as a configured endpoint. On request failure, `internal/plugin/builtin/opendht/opendht.go:175–189` logs the full URL and includes it in the returned error. `TestAuditOpenDHTProxyURLCredentialsReachFailureError` confirmed that the error contains the synthetic password (`security-audit-evidence/opendht-proxy-url-credential-leak.txt`). Desktop `internal/ctrl/establish.go:68–70` logs this error; mobile `mobile/controller.go:301–305` sends it to the app's rolling log. The Android app also leaves URL userinfo in the configuration section of its manual “secrets redacted” log export (A-22). This requires a proxy URL with embedded credentials, which the default public proxy does not use; the demonstrated exposure is local logging or a user-shared export, **not** automatic network exfiltration.

**Fix:** Reject URL userinfo or store credentials separately from the display URL. Redact both configured URLs and all error/log paths before sharing; test single and list endpoint settings, request failure, fallback and export. Avoid putting credential-bearing URLs into structured log fields.

## Verification and limits

The baseline passed `go mod verify`, `go vet`, race-enabled unit tests with `builtin_all,mobile`, cross-builds for Linux/Windows/FreeBSD/macOS, and optional Cloudflare module race tests. Both optional OpenDHT process-plugin smoke scripts also passed against local synthetic HTTP servers (`security-audit-evidence/opendht-script-smoke.txt`). Staticcheck 2026.2rc1 with `builtin_all,mobile,security_audit` emitted no findings; this does not replace the manual review, which found G-01. The full race-enabled suite with `security_audit` passed after fixing an assertion in the audit test that depended on wireguard-go's map iteration order; the synthetic rogue peer held the route in both orders. The targeted attack test then passed 100 repeated race-enabled runs. Audit-tag tests reproduced G-01, G-03, G-04, G-14–G-17 and the reflection/process-plugin cases using generated synthetic material; G-14–G-16 targeted tests also passed with the race detector. Both imported-profile UAPI injection variants passed targeted race-enabled Go tests. The mobile STUN decoder passed a one-hour unguided campaign of 641,779,369 fuzz executions with no crash (37.9% coverage for that package under the harness). A separate one-hour coverage-guided OpenDHT parser campaign passed 63,544,592 executions with no crash (`security-audit-evidence/opendht-fuzz-guided-1h-summary.txt`). Another one-hour coverage-guided mobile STUN parser campaign passed 383,576,214 executions with no crash (`security-audit-evidence/mobile-stun-fuzz-guided-1h-summary.txt`). A one-hour coverage-guided NaCl endpoint-record parser campaign passed 129,622,592 executions with no crash (`security-audit-evidence/crypto-fuzz-guided-1h-summary.txt`). A one-hour coverage-guided mobile JSON-to-UAPI configuration campaign passed 100,219,138 executions with no crash (`security-audit-evidence/mobile-config-fuzz-guided-1h-summary.txt`); this does not negate G-01, which concerns accepted but unsafe values. Config-parser fuzzing found G-13 and stopped after minimizing/reproducing it. A follow-up filtered out that known nil-key class. Its first run was invalidated by an investigator-sent SIGQUIT during minimization, not a reproduced source crash; a three-minute diagnostic rerun passed 925,819 executions (`security-audit-evidence/config-filtered-fuzz-diagnostic.txt`). A separate one-hour coverage-guided OpenDHT plugin-constructor campaign passed 78,756,311 executions with no crash (`security-audit-evidence/opendht-config-fuzz-guided-1h-summary.txt`); accepted configurations still require the G-05/G-11/G-17 policy checks. No NAS credential, production key, public DHT record, or real peer was used.

A redacted history pattern scan inspected 1,599 blobs across 519 commits for common PEM private keys, AWS/GitHub/Stripe/Slack token formats and HTTP URL userinfo, finding zero matches (`security-audit-evidence/go-secret-pattern-scan.json`). It does not detect every secret shape or malicious change.

This review did not audit all transitive libraries/Go/Android/OpenDHT internals, establish byte-for-byte AAR provenance, run an Android OS VPN, or test the home's NAT pair. Static analysis/fuzzing cannot prove absence of backdoors. No compromised dependency or real-world exploitation was established.

**Release gate:** fix G-01 and retest the actual Android APK; reject G-14 low-order keys; decide the discovery-authentication policy; harden G-03–G-05 and make G-13 malformed config fail cleanly; set a safe G-08 refresh cadence; remove unused plugin code; fix G-12 before enabling release workflows; produce verifiable fork-built AAR/APK/container; then run the planned external-network and Android-phone tests before enabling entry to the home network.
